## 2. Magisk 刷入可行性（已验证到"未刷"阶段）

### 2.1 结论

- **技术上可行**，但**风险高**，且**标准备份/救砖通道不完整**。
- 已生成可用补丁包，但**没有写入分区**。

### 2.2 关键发现

1. `boot_b` 里的 ramdisk 是 **recovery ramdisk**（含 `/sbin/recovery`、`res/images/*`、`init.recovery.ecarxp.rc`），出厂正常启动时 **LK 传 `skip_initramfs`**，所以这个 ramdisk 平时根本不执行。
2. Magisk 的 legacy SAR 补丁会把**内核里的字面量** `skip_initramfs` hexpatch 成 `want_initramfs`，从而强制内核加载 ramdisk，再由 magiskinit 挂 system 继续启动。
   - 实测该内核里确实存在这个字符串，补丁落在解压后偏移 `0x124D447`。
3. boot.img **无 AVB footer、全盘无 vbmeta**，LK 里虽有 MTK secure boot(SBC) 代码，但镜像本身无签名块 → 大概率不校验（**未 100% 证实**）。
4. 四个鱼眼摄像头与 AVM 渲染都在 native（`/vendor/bin/carlinx_avm_main`），与 Magisk 无关。

### 2.3 已生成的产物

路径：`D:\ARM\Auto\p145-magisk\`

| 文件 | 说明 |
|---|---|
| `boot_a.img` / `boot_b.img` | 双槽完整备份（32MB/个） |
| `new-boot.img` | Magisk v31.1 + `LEGACYSAR=true` 打出的补丁镜像（32MB） |
| `para.img` / `lk_b.bin` / `seccfg.bin` | 关键分区备份 |
| `inspect_boot.py` / `unpack_ramdisk.py` | 分析脚本 |

补丁内容核对：`/init` 已替换为 magiskinit，`overlay.d/sbin/{magisk,init-ld}.xz` 就位，`.backup/.magisk` 为 `KEEPVERITY=true KEEPFORCEENCRYPT=true RECOVERYMODE=false PREINITDEVICE=userdata`。

### 2.4 为什么没刷

- 没有 recovery 分区；fastboot 锁定且只走 USB；EDL 需要 USB 连接 + BROM 进入条件。
- 一旦起不来，**车内没有可用救砖通道**，只能拆机/短接。
- 结论：**除非先验证 USB/EDL 通道可用，否则不建议刷**。

### 2.5 若坚持要刷的最小风险流程

1. USB 连车机，验证 `adb reboot edl` + `python mtk.py printgpt` 能读分区，再 `mtk.py reset` 回来；
2. 备份 `boot_b`、`para`、`lk`、`seccfg`（已有）；
3. 只写 `boot_b`，`boot_a` 保持原厂；
4. 刷完 `sync`，一次完整启动，别断电；
5. 起不来：EDL → `mtk.py w boot_b boot_b.img` → `mtk.py reset`。

> 备选：不动 boot，用"系统内 root"满足大部分需求（本机已具备 adb root + rw /system）。

## 3. 屏蔽「智能巡航已退出」语音播报

### 3.1 链路定位


### 3.2 走过的弯路（重要）

| 方案 | 结果 |
|---|---|
| RRO 覆盖 SAL 的资源字符串 `sal_icc_not_activate_icc_quit` | ❌ 无效。SAL 不读资源，直接把文本字面量传给 DuerOS |

## 4. 音量键 / 方控 / 旋钮 始终调节媒体音量

> **状态：✅ 运行中（2026-11-05 曾短暂停用，已恢复）。** 停用原因：诊断旋钮丢键时反复强杀 Frida 注入进程，留下"半截 hook"导致音量方法抛异常。教训：**不要 `pkill frida-inject16` 强杀常驻注入**；要停就停守护 + 重启对应目标进程。恢复后的部署见第 5 章。

### 4.1 机制

本车为 Android Automotive，音量按**音量组**管理（不是按 stream）：

| groupId | 用途 |
|---|---|
| 0 | 媒体（MEDIA） |
| 1 | 通话 |
| 2 | 语音（VR） |
| 3 | 系统提示 |
| 4 | 导航（NAVI） |
| 5 | 外放（EXT_SOUND） |
| 6 | 铃声 |

按键路径（`com.android.car.CarAudioService`，jadx 自 `CarService.apk`）：

```java
private final AudioPolicy.AudioPolicyVolumeCallback mAudioPolicyVolumeCallback = ... {
    public void onVolumeAdjustment(int adjustment) {
        int usage = CarAudioService.this.getSuggestedAudioUsage();          // 当前焦点 usage
        int groupId = CarAudioService.this.getVolumeGroupIdForUsage(usage); // 映射到组
        ...
        CarAudioService.this.setGroupVolume(groupId, currentVolume + 1, ...);
    }
};
```

`getSuggestedAudioUsage()` 在整个 CarService 里**只有一个调用点**（就是上面这个音量回调）。

### 4.2 实现

Hook `com.android.car.CarAudioService.getSuggestedAudioUsage()`，恒返回 `USAGE_MEDIA`（1）：

```js
Java.perform(function () {
    var S = Java.use('com.android.car.CarAudioService');
    var orig = S.getSuggestedAudioUsage;
    S.getSuggestedAudioUsage.implementation = function () {
        var r = orig.call(this);
        console.log('[VOL] suggested usage=' + r + ' (force 1=USAGE_MEDIA)');
        return 1;
    };
    console.log('[VOL] hook installed');
});
```

### 4.5 方控（方向盘按键）路径：keyserver

**现象**：hook 了 `CarAudioService.getSuggestedAudioUsage()` 后，adb 注入的音量键已经锁媒体，但**方控**仍然调"当前活跃通道"（语音说话时改的是 group=2）。

### 5.1 架构（EVCC「自启」= Managed Attach）

```
EVCC 启动 / 开机
  └─ KeepAliveService 读 /data/data/com.kooo.evcc/shared_prefs/evcc_frida.xml
       └─ autostart_scripts 里每条映射
            ├─ 生成 /data/local/tmp/evcc/frida/evcc_as_<key>.sh（2 秒轮询 pidof 的看护脚本）
            └─ 目标进程 pid 变化 → evcc_dbg -p <新pid> -s evcc_as_<key>.js 重新注入
```

**4 条映射（已写入 `evcc_frida.xml`）**：

| autostart key | 目标包 | 脚本 |
|---|---|---|
| `custom_icc_mute` | `com.baidu.che.codriver` | `icc_mute.js` |
| `custom_vol_car` | `com.android.car` | `vol_car.js` |
| `custom_vol_keyserver` | `com.flyme.auto.keyserver` | `vol_keyserver.js` |
| `custom_vol_knob` | `com.flyme.auto.knobservice` | `vol_knob.js` |

- 一个脚本只对一个包（Frida 一次只能挂一个进程），所以 4 个脚本而不是 2 个；
- 目标进程重启 → pid 变化 → 看护脚本自动补挂，**不需要重启车机**；
- 注入是 **Attach（挂进正在运行的进程）**，不会重启目标进程。

### 5.2 注入方式核对（Attach / Spawn / Daemon）

目标进程输入框下方有三个单选，另有一个独立的「自启」开关：

| 模式 | 代码入口 | 实际行为 | 重启目标进程？ |
|---|---|---|---|
| **Attach**（默认，当前选中） | `FridaEngine.inject()` | `pidof` 找当前 pid → `doInject(pid)` 挂进去 | 否 |
| **Spawn（早期注入）** | `FridaEngine.spawnInject()` | 先重启目标进程，再在启动早期注入 | **是** |
| **Daemon（持久）** | `FridaEngine.startManagedDaemon()` | 生成带健康检查 / pid 历史 / 隔离的看护脚本 | 否（首次 attach） |
| **自启开关**（脚本卡片） | `KeepAliveService` 的 `[Managed Attach]` 分支 | 生成 `evcc_as_<key>.sh`：2 秒轮询 `pidof`，pid 变了就重注 | 否 |

**结论**：

- 三个单选只影响**手动点「执行」**那一次；
- 「自启」开关**固定走 Managed Attach**，不会重启系统进程（此前记的「开机 Spawn」是误读，已更正）；
- 所以不用担心"每次开机都重启 car 进程"。

> ⚠️ **实测教训（2026-11-06 19:00-19:05）**
> 用「执行」跑出来的会话实际是 **Spawn** 模式：目标进程一退出，EVCC 会话就每 ~6 秒 `force-stop` + 重启一次再注入，连跑 20 多轮（`hook_fh_2` → `hook_fh_28`），最后把 `system_server` 拖到重启 —— 车机表现为**反复弹回充电界面 / 一直抢焦点**，负载冲到 38。

### 8.1 证据

1. `dumpsys display`：只有一块物理屏 1920×1080（中控），`/dev/graphics` 只有 `fb0`；

## 9. 免唤醒语音指令自定义

### 9.1 配置位置

```
/data/data/com.baidu.che.codriver/databases/vrSetting.db
  ├─ vrSetting         ：总开关等（free_wakeup_word_config = 1 已开启）
  └─ vrTextConfig id=9 ：JSON 数组，免唤醒指令列表（原 46 条）
```

单条结构：

```json
{"name":"我想听XXX","state":true,"type":"media","word":"我想听"}
```

类型：`media` / `navigation` / `car_control` / `global` / `function`。

原有相关条目：

| name | word | type | state |
|---|---|---|---|
| 我想听XXX | 我想听 | media | ✅ |
| 我要听XXX | 我要听 | media | ✅ |
| 导航去+地名 | 导航去 | navigation | ✅ |
| 打电话给+人名/号码 | 打电话给 | function | ✅ |

### 9.2 研究过程与结论（2026-11-05）

**结论：不能自定义新的免唤醒词。** 只能从预置列表里勾选启用/禁用。

三步验证：

1. **数据库列表只是 UI 配置**
   往 `vrTextConfig` 的 JSON 追加 `{"name":"播放一首XXX","state":true,"type":"media","word":"播放一首"}`（46→47 条），重启 DuerOS 后条目仍在，但**完全没效果**。

2. **找到引擎真正拿到的词表**（运行时 hook）

   ```
   WakeUpWordsConfig.getFreeWakeUpWords() → [我想听|我要听|导航去|导航到|附近的|打电话给|我想查询]
   WakeUpControl.setKwDynamicConfig(JSONObject)
   {"kwd.enable-keyword":[...],"kwd.disable-keyword":[...],
    "wp.aks_enable":true,"words":["你好银河","你好吉利"]}
   ```

   「播放一首」最初落在 `kwd.disable-keyword`，后来被强行塞进 `kwd.enable-keyword` 第一位：

   ```json
   "kwd.enable-keyword":[...,"我想听","我要听","播放一首"]
   ```

3. **引擎接受配置，但不认这个词**
   - `WakeUpEngine.setKwdConfig(json)` 返回 `0`（成功）
   - `WakeUpEngine.aksGetWordsScore("播放一首")` 无报错
   - 重启唤醒引擎（`stopWakeUp` / `startWakeUp`）后实测：
     - 「播放一首爱在西元前」→ **无反应**
     - 「我想听爱在西元前」→ **正常**

**原因**：KWS 声学模型是**预置词库**，`kwd.enable-keyword` 只是对词库做过滤（允许/禁止），不是把任意文本动态编进模型。新增词永远不会被识别。

**UI 侧**：语音设置里只有「唤醒与聆听 → 场景免唤醒 / 场景免唤醒开关」，没有自定义指令入口。

### 9.3 可行替代

| 方案 | 说明 |
|---|---|
| 用「我想听+歌名」 | ✅ 现成可用（免唤醒） |
| 带唤醒词说「你好银河，播放一首X」 | ✅ 可用，只是需要先唤醒 |

## 12. 踩过的坑（写给未来的自己）

1. **RRO 改 SAL 字符串没用** —— SAL 直接传文本给 DuerOS，不查资源。
2. **TTS 缓存不能改短** —— 引擎校验分段/长度，改短即 `cacheError` 并重新合成。
3. **Frida 版本敏感** —— 16.7.19 稳定；17.25 在本机注入会崩；EVCC 自带 17.23.3 稳定。
4. **PowerShell 里不要写 `$(pidof ...)`** —— 会本地展开；先取值再拼命令，或写成 .sh 推上去跑。
5. **`/sdcard` 上的 frida 二进制不能直接执行** —— 放 `/data/local/...`（exec 挂载）再跑。
6. **车机休眠掉 adb** —— 重新 `adb connect`，必要时 `adb kill-server`。
7. **改系统 APK 会破签名** —— 但本机平台 key 是 AOSP testkey，可"改完用同证书重签"，签名记录不变。
8. **AVM 的四路鱼眼不是 Camera2** —— 第三方 App 拿不到，只有 `carlinx_avm_main` 内部有。
9. **仪表不是 Android** —— 中控没有任何渲染/单位配置入口。
10. **`dumpsys car_service` 属性要区分 areaId** —— 部分属性 `area 0` 读不到（如 `TRIP_GRAPH_RANGE_OPTION` 需要 area 1）。
11. **音量不是按 stream，是按 volume group** —— 0 媒体 / 1 通话 / 2 语音 / 4 导航；按键跟随"当前焦点 usage"，改 `getSuggestedAudioUsage()` 即可锁组。
12. **CarService 的类在 APK 里（不是 vdex）** —— `CarService.apk` 含 classes.dex，可直接 jadx 分析；`GeelyAudioService.apk` 则只有 vdex，无 dex。
13. **EVCC 的 `root_automation_config.json` 不要手改** —— 用 UI 的"规则导入 / 我的上传"；`--@autostart` 的 Lua 走 `/sdcard/Download/EVCC/scripts/lua/` 自动扫描。
14. **两个 hook 已解耦** —— 一个功能出问题只杀对应守护，不影响另一个。
15. **`pkill -f` 会匹配到自己** —— 在 `adb shell "pkill -f event4"` 里，shell 命令行本身包含 `event4`，会把自己杀掉（表现为无输出、exit 1）。要把 pkill 写进 .sh 文件再执行。
16. **音量有三个入口，分别在不同进程** —— Android 音量键走 `CarAudioService`；方控走 `com.flyme.auto.keyserver`；旋钮走 `com.flyme.auto.knobservice`（SmartButton）。只 hook 一处，另外两处照旧。定位方法：在 `CarAudioService.setGroupVolume` 里打印 `Binder.getCallingPid()`。
17. **注入去重不能靠"目标进程里写标记"** —— 标记写入有延迟/失败时，守护会每轮重复注入（进程数越堆越多）。正确做法：守护记录「注入器 pid」+「目标进程 pid」，两者都有效才跳过（见 `p145_guard.sh`）。
18. **Frida 可以"无进程常驻"** —— `frida-inject -e`（eternalize）注入后立即退出，hook 留在目标进程里；守护只按「目标 pid 是否变化」去重。验证看 `hits.log`，不要用 `ps | grep frida` 判断是否生效。
19. **eternalize 不能热替换** —— 改了 hook 脚本后旧 agent 仍在，必须重启对应目标进程（或重启车机）才会加载新代码。
20. **停 hook 只能靠重启目标进程** —— 关开关、杀注入器、杀守护都只是"不再重新注入"；已经挂进进程的 hook 会一直留到该进程重启。2026-11-05 音量整体失效就是强杀注入器造成的半截 hook。
21. **EVCC「自启」不是 Spawn，是 Managed Attach** —— UI 提示写"开机 Spawn + Daemon 保活"容易误读；实际是 `KeepAliveService` 生成 `evcc_as_<key>.sh`，2 秒轮询 `pidof`，pid 变了才 attach 重注，**不会重启目标进程**（第 5.2 节）。
22. **EVCC 的 Frida 脚本按"一个脚本一个包"拆** —— 不要像 shell 版那样一个 `hook_volume_all.js` 靠进程名分支，因为 EVCC 每条自启只绑定一个目标包。
23. **shell 守护会莫名消失** —— 2026-11-06 就丢过一次 `vol_guard`（目标进程换了 pid 也没人补挂）。这就是换 EVCC 的直接原因：EVCC 有保活服务，比裸 shell 循环抗清理。
24. **EVCC 的「执行」= Spawn，会重启目标进程并自我重试** —— 开了「自启」之后再点「执行」等于同时开了两套：会话每 ~6 秒 force-stop 一次目标，20 多轮后 `system_server` 被拖崩重启（车机表现为反复弹回充电界面、焦点乱抢、load 冲到 38）。**只用「自启」，不要点「执行」**；framework 重启后 EVCC 的会话表会清空，只剩看护脚本，状态自然恢复。
25. **Android framework 重启 ≠ 车机重启** —— 这次 `adb` 掉了十几秒又回来，`uptime` 仍是 1:17，但所有 app pid 全变（`system_server` 重启）。判断方法：`pidof system_server` 与 `uptime` 对照。framework 重启会把 EVCC 内存里的会话清空，但 `/data/local/tmp/evcc/frida/evcc_as_*.sh` 看护脚本会存活并补挂。
26. **Frida 17.23.3 不能注入 DuerOS（com.baidu.che.codriver）** —— 不管是 Spawn 还是 Attach，都会在 `bds-engine` / `.bcebos.com` 线程里 SIGSEGV，栈顶是 `/memfd:frida-agent-64.so` 调 `sscanf`。表现为**语音助手一唤醒就没了**。16.7.19 同位置稳定。所以 ICC 这条链路永远用 `frida-inject16 -e`（attach），不要用 EVCC 的 17.23.3。
27. **EVCC「自启」= 开机 Spawn + 会话重试** —— 不只是 pid 看护；开机会 force-stop 目标再早期注入，失败还会每 ~6 秒重试。系统进程（尤其 DuerOS）扛不住。结论：**EVCC 自带 Frida 在本机只适合不碰 DuerOS 的场景**。
28. **`am force-stop com.kooo.evcc` 会短暂断 adb** —— 车机的 adb 链路挂在 EVCC 上；force-stop 后十几秒 `device offline`，会自动回来。要做"停 EVCC + 改配置 + 重启进程"的连续动作，必须写成设备端脚本用 `nohup` 跑，不能靠一条 adb 命令串。
29. **「桌面崩溃黑屏」先查 system_server 有没有死** —— 快速判定：`uptime` 没断（说明没整车重启）+ `pidof system_server` 变了 + `logcat -b events | grep am_crash` 里有 `system_server`。本机这次是 `NetworkStatsService` 采样线程在 `SystemClock.currentNetworkTimeMillis()` 拿到 `DeadObjectException` → 包成 `DeadSystemException` → `BestClock` 只 catch `DateTimeException` 不 catch 它 → 系统进程未捕获异常 → 框架整体重启。6 天内第 5 次，栈完全一致，属 ROM 问题，与我们无关。
30. **崩溃现场都在 EMS 里，比 logcat 靠谱** —— `/data/misc/ems_logs/snapshot/` 有 `SYSTEM_SERVER_JE@<pid>_…txt`（异常栈）和 `zipLog/*.zip`（含崩溃瞬间的 main/system/events 全量日志）；`/data/system/dropbox/` 有 `system_server_crash@*`。logcat 的 main buffer 到崩溃那刻就断了，EMS 快照才是完整现场。
31. **Lua 自启依赖 EVCC AutomationService** —— `--@autostart true` 是在 `AutomationService` 里排队执行的（`h20.java: ScriptEngine: autostart: N script(s) queued`）。`root_automation_config.json` 里 `serviceEngineRunning: false` 时，Lua 自启**根本不会跑**，两个 hook 会静默消失。这解释了 11-06 20:56 重启后守护没回来的问题。判断守护是否真在跑：`ps -A | grep ttsguard`，不要只看 Lua 文件还在不在。

## 14. 桌面黑屏「自动重启」事件分析（2026-11-07 11:43）

**用户看到的现象**：放着歌，桌面突然崩溃、黑屏，随后桌面自己回来了。

**实际发生**：不是桌面 App 崩，也不是整车重启，而是 **Android framework（system_server）整体崩溃后软重启**。

| 时间 | 事件 | 证据 |
|---|---|---|
| 11:43:14 | 旧 system_server（pid 1692）崩溃 | `am_crash: [1692,0,system_server,…DeadSystemException…]` |
| 11:43:37 | 新 system_server（pid 32282）起来 | `boot_progress_start: 8130175` |
| 11:43:44 | 屏幕重新使能，桌面/状态栏回来 | `boot_progress_enable_screen` |
| — | **车机没有重启** | `uptime` 14:49h，上次开机 11-06 20:56 |

### 14.1 崩溃栈

`/data/system/dropbox/system_server_crash@1794022994047.txt`（与 EMS 快照 `SYSTEM_SERVER_JE@1692_…` 完全一致）：

```
java.lang.RuntimeException: android.os.DeadSystemException
	at android.os.SystemClock.currentNetworkTimeMillis(SystemClock.java:287)
	at android.os.SystemClock$3.millis(SystemClock.java:312)
	at android.os.BestClock.millis(BestClock.java:49)
	at com.android.server.net.NetworkStatsService.performSampleLocked(NetworkStatsService.java:1342)
	at com.android.server.net.NetworkStatsService.performPollLocked(NetworkStatsService.java:1324)
	at com.android.server.net.NetworkStatsService$HandlerCallback.handleMessage(NetworkStatsService.java:1697)
	at android.os.HandlerThread.run(HandlerThread.java:65)
```

同时 crash buffer：

```
*** FATAL EXCEPTION IN SYSTEM PROCESS: NetworkStats
DeadSystemException: The system died; earlier logs will point to the root cause
```

**机理**：流量统计（NetworkStats）后台采样线程去取「网络时间」→ `network_time_update_service` 的 binder 返回 `DeadObjectException` → 被 `rethrowFromSystemServer()` 包成 `DeadSystemException`（RuntimeException）→ `BestClock.millis()` 只 catch `DateTimeException`，不 catch 它 → 异常冒到 HandlerThread 顶端 → **system 进程内未捕获异常 = 整个框架被杀**。

旁证：崩溃前 `BestClock: java.time.DateTimeException: Missing NTP fix` 每 6 秒一条 —— 本机 NTP 从来没同步成功过（`persist.sys.ntp.server` 为空，`auto_time=1`）。

### 14.2 不是我们改的东西导致的

- 崩溃时车上**一个 Frida 都没有**：EVCC 的 4 条 Frida 自启已于 11-06 19:20 清空，两个 shell 守护在 11-06 20:56 整机重启后也没再起来（见 14.3）；
- 同样的栈在本机已出现 **5 次**，五次完全一致：

| 时间 | 快照 |
|---|---|
| 2026-11-01 23:36 | `SYSTEM_SERVER_JE@1652_…` |
| 2026-11-04 19:53 | `SYSTEM_SERVER_JE@1600_…` |
| 2026-11-05 07:55 | `SYSTEM_SERVER_JE@30943_…` |
| 2026-11-06 19:03 | `SYSTEM_SERVER_JE@1741_…`（这次叠加了 Frida Spawn 风暴） |
| 2026-11-07 11:43 | `SYSTEM_SERVER_JE@1692_…` |

→ 这台车 **ROM/框架层的老毛病**，约 1–2 天一次，触发时刻随机。

### 14.3 能不能修

- **改不了**：要修得动 `NetworkStatsService` / `SystemClock`，属于 framework，需要改 ROM；本机没刷 Magisk，也不值得为这个刷。
- **别用 Frida 去 hook system_server 兜**：注入系统进程风险远大于收益，正是 11-06 踩过的坑（第 12 章第 24/26 条）。
- **只能缓解**：定期灭车/重启（别连续挂机好几天）、减少后台常驻、留意 OTA。

### 14.4 这次暴露的真问题（已处理）

framework 崩溃 → 4 个目标进程全重启 → hook 全丢；而 11-06 20:56 整机重启后，两个 shell 守护**根本没回来**（`icc_guard.log` 最后一次注入还是 11-06 19:20）——也就是说 **ICC 屏蔽和音量锁媒体从昨晚起一直是关的**。

### 14.5 待办：让功能扛得住重启

现在的自启链是断的，每次整机重启 / 框架崩溃后功能都会哑。候选方案：

### 15.3 架构

```
MainActivity（现代化深色 UI）
   ├─ 状态卡：ADB 通道 / Root 权限 / Frida 运行时
   ├─ 功能卡：ICC 播报屏蔽、音量锁媒体（PillSwitch 自绘开关）

GuardService（前台服务，常驻通知）
   └─ 每 N 秒（默认 5）：HookManager.sync()

```

### 15.4 关键实现点

**① App 自己拿 root（不需要 su、不需要 root 安装）**

本机 `ro.adb.secure=0` 且 adbd 常驻 root（`adb shell id` → `uid=0(root) context=u:r:su:s0`），
`netstat` 里 adbd 监听 `:::5555`（含 loopback），所以 App 直接对 `127.0.0.1:5555` 说 ADB 协议即可拿到 root shell。
`AdbClient` 用 24 字节小端报文头（command/arg0/arg1/len/crc/magic）实现，约 250 行。

**② 一次连接做完巡检**（省电、省开销）

```
echo "U=$(id -u)";
echo "X=$(test -x /data/local/p145adv/frida-inject16 && echo 1 || echo 0)";
echo "@com.android.car=$(pidof com.android.car)";   ← 4 个目标同理
```
正常一轮守护只开 1 条 adb 连接；实测 App 常驻 CPU **0.0%**。

**③ 注入判定靠注入器输出**

`frida-inject16 -e`（eternalize）加载完 agent 就退出，所以**同步执行**并直接读 stdout：

```sh
cd /data/local/p145adv && timeout 25 ./frida-inject16 -e -p <pid> -s hook_xxx.js 2>&1 | tee logs/<key>.log
```

输出含 `[ICC] hook ok` / `[CAR] hook ok` / `[KEY] hook ok` / `[KNOB] hook ok` → 记为已注入。
（踩坑：用 `nohup ... &` 后台跑时，adb 会话一断子进程就被回收，日志永远是空的，见 15.9）

**④ 关闭开关 = 重启目标进程**

hook 一旦注入就常驻，只能靠重启目标进程卸载。所以关开关会顺手
`kill -9 $(pidof <pkg>)`，让系统重新拉起，界面立刻变「已关闭」。

### 15.9 踩坑（写给自己）

1. **ADB 协议错位会 OOM** —— 握手阶段收到 `CNXN` 必须先把它的 payload 读掉再继续，否则后续按 len 解析会读到垃圾长度（当场 1.9 GB 分配 OOM 崩掉守护）。现在加了 `checkLen()`（>256 KB 直接抛协议错位）。
2. **`nohup ... &` 在这个 adb 会话里活不下来** —— 会话一关子进程就被回收，日志文件是空的、hook 没注入。改成**同步执行** `timeout 25 frida-inject16 -e ...`，输出直接当判定依据。
3. **O+ 隐式广播后台限制** —— `am broadcast -a com.p145.adv.ICC_ON` 报 `Background execution not allowed`，常量根本没生效。两个解法都做了：`targetSdkVersion=25`（绕开限制）+ 命令文件通道。
4. **hits.log 写不进去** —— 目录 755 root，目标进程是 uid 1000，`FileOutputStream` 失败被 JS `catch` 吞掉。部署时 `touch + chmod 666`。
5. **app 图标用 vector 可以**，但 `aapt2 dump badging` 里 `icon=''` 属正常（车机桌面是卡片式，不显示图标）。
6. **卸载/重装不会丢配置** —— 配置在 SharedPreferences，但 `/data/local/p145adv` 是 root 目录，重装后仍复用（脚本版本号变了才会重部署）。


| 场景 | 结果 |
|---|---|
| `force-stop`（`stopped=true`）后发 `am broadcast -a com.p145.adv.START` | ❌ 广播被丢弃，进程不起，`stopped` 仍是 true |

这样即使被系统清理或强行停止，也能在一个周期内自动恢复。

### 15.21 三种「拉起 App」的方式区别（关于页已补兜底命令）

之前关于页只列了广播命令，容易误解成"发个广播就能从任何状态拉起"。实测三种方式差别很大：

| 方式 | 是不是广播 | `stopped=false` | `stopped=true`（被强行停止） | 弹 UI |
|---|---|---|---|---|
| `am broadcast -a com.p145.adv.START`（或 `INJECT`） | 是 | ✅ 有效 | ❌ 广播被系统直接丢弃 | 否 |
| `am start-foreground-service -n com.p145.advancedsettings/.GuardService` | **不是**，是直接启动服务 | ✅ | ✅ **能拉起来，并把 stopped 清成 false** | 否 |
| `am start -n com.p145.advancedsettings/.MainActivity` | 不是，是启动界面 | ✅ | ✅ | 会弹界面 |

结论：**广播只在 App 正常存活时才有效**；被强行停止（或某些开机场景）之后，只有
`start-foreground-service` / `start` 这类「直接给组件」的命令才能把它拉回来。
所以 EVCC 的开机规则（15.20）用的是前者，不弹界面。
